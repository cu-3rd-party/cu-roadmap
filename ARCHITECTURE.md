# Архитектура и Требования проекта: Система рекомендаций студенту (Roadmap)

## 1. Цели и задачи
**Финальная цель проекта**: Построение полной Roadmap’ы студента от момента поступления в ЦУ до его приема на работу.
**Суть MVP**: На основании предпочтений и/или навыков студента сайт подбирает пользователю курсы внутри ЦУ, помогая выбрать правильную траекторию обучения с учетом требований к Major'у, общих требований УО, пререквизитов и желаемой нагрузки. 

### Боль пользователя
Раз в семестр студент сталкивается со сложным выбором курсов, ограниченным различными правилами ЦУ (пререквизиты, кореквизиты, обязательные курсы). Студент часто не понимает, какие курсы нужно брать для определенного направления. Система берет эту сложность на себя.

## 2. Функциональные требования (Пользовательские сценарии MVP)
- **Сценарий 1: Автоматическое построение плана под мейджор**. Студент указывает пройденные курсы, выбирает желаемый Major и задает максимальную нагрузку (load). Система генерирует оптимальный пошаговый план до выпуска.
- **Сценарий 2: Подбор мейджора на основе интересов**. Студент набирает курсы в корзину. Система подсказывает, к какому Major студент ближе всего, и оценивает реалистичность плана.
- **Сценарий 3: Свободный конструктор (Ручное планирование)**. Студент сам расставляет предметы, а система работает как валидатор: предупреждает при нарушении правил пререквизитов/кореквизитов. При выборе Major система может "дописать" недостающие курсы в свободные слоты.
- **Сценарий 4: Планирование ради конкретной цели**. Студент фиксирует желание пройти один конкретный курс в строго определенном семестре, система выстраивает весь остальной маршрут вокруг этой цели (если это не нарушает правил).

*Ограничения MVP:* Без интеграции с hh.ru, без автоматического парсинга LMS (пока ручной ввод), нет админки для УО, нет данных об отчислениях (вероятность фейла пока не учитываем в MVP, но держим в уме).

## 3. Технический стек и Инфраструктура
- **Язык**: Python
- **Фреймворк**: FastAPI
- **База данных**: PostgreSQL (рекомендуется v15) + SQLAlchemy
- **Контейнеризация**: Docker
- **Веб-сервер / Reverse Proxy**: Caddy (ВНЕ docker-контейнера приложения)
- **Управление графами**: NetworkX (для реализации DAG)
- **Окружения**: Prod и 2 Test окружения в Docker-контейнерах, настроенный CI/CD
- **Frontend**: React
- **Аналитика**: Яндекс Метрика
- **Домен на время MVP**: courses.cu3rd.ru (в будущем переезд в LMS)

## 5. Структуры данных и База данных
### `courses` (Курсы)
- `id` (UUID)
- `title` (String) - Официальное название
- `description` (Text)
- `handbook_link` (Text)
- `course_type` (Enum: mandatory, elective, etc.)
- `category` (Enum: stem, soft, business, tech)
- `allowed_cohorts` (Array/JSON) - для каких потоков (2024, 2025)
- `available_semesters` (Array of Integers) - в каких семестрах читают
- `recommended_semester` (Integer) - nullable
- `workload` (Integer/Float) - Нагрузка
- `csat_metric` (Float) - CSAT студентов

### `course_dependencies` (Связи курсов)
- `id` (UUID)
- `course_id` (FK -> courses) - Какой курс берем
- `required_course_id` (FK -> courses) - Какой курс нужен
- `dependency_type` (Enum: `prerequisite`, `corequisite_type1`, `corequisite_type2`)
  - *Type 1*: курсы изучаются одновременно в одном семестре (объединяются в супер-узел).
  - *Type 2*: курс A требует курс B, но B можно проходить отдельно, либо вместе в одном семестре.

### `majors` (Мейджоры)
- `id` (UUID)
- `title` (String) - (swe, ai, business)
- `school` (String) - (tech, design)

### `major_requirements` (Требования Мейджора)
- `major_id` (FK -> majors)
- `course_id` (FK -> courses)
- `requirement_type` (Enum: core, minor_recommended)

### `students` и `student_passed_courses`
- `students`: `id` (UUID), `cohort` (Integer), `current_semester` (Integer), `target_major_id` (FK)
- `student_passed_courses`: `student_id` (FK), `course_id` (FK)

## 6. Движки и Математические модели
В проекте предусмотрено два движка планирования:

### Engine 1: Продвинутая модель на графах (DAG)
Базируется на теории графов, задаче удовлетворения ограничений и векторном поиске (в будущем).
1. **Жесткая логика**: Пространство курсов = DAG. Узлы = курсы, Ребра = пререквизиты/кореквизиты.
2. **Алгоритм**: `Topological Sort` + `Bin Packing`. Сортируем оставшиеся курсы так, чтобы не нарушить правила, затем "упаковываем" в семестры с учетом лимита нагрузки `workload`.
3. **Предикт Major'а**: Вычисление Коэффициента Жаккара (Jaccard Index) между выбранными курсами и обязательными курсами Major'а.

### Engine 2: Максимально простая матмодель (Жадный алгоритм)
Используется как fallback или для быстрого запуска:
1. Вычисляются курсы, требуемые для Major, вычитаются пройденные.
2. Выбираются курсы, чьи пререквизиты уже закрыты (`availableCourses`).
3. Сортируются по количеству "открываемых" ими последующих курсов (наиболее важные идут первыми) и по `recommendedSem`.
4. Жадно добавляются в план семестра до лимита нагрузки `studentLoad`.

## 7. Best Practices для Агентов
1. **Строгая типизация**: Использовать Pydantic схемы (v2) для валидации всех входов/выходов API.
2. **Изоляция бизнес-логики**: Роутеры (API) не должны содержать бизнес-логику. Вся логика графов, построения планов и валидации должна быть инкапсулирована внутри папки `services/`.
3. **Обработка Corequisites**: Особое внимание уделять `corequisite_type1` (курсы-близнецы) — при построении плана они должны "склеиваться" в один шаг с суммарной нагрузкой.
4. **Асинхронность**: Использовать `async`/`await` для всех операций с базой данных (использовать асинхронный драйвер для SQLAlchemy, например, `asyncpg`).
5. **Чистота наименований**: Использовать официальные названия курсов и дисциплин, избегать сленга (типа "бизнесаны") для упрощения дальнейшего парсинга данных.
6. **Готовность к расширению**: Оставлять заглушки (или не жестко хардкодить) под будущую метрику "Риск фейла (P_fail)" и векторное сопоставление навыков (Cosine Similarity) для парсинга с hh.ru.
